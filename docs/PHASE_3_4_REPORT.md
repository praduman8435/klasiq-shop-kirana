## Portal route decision

One route audited against the brief's two suggestions (`/track`,
`/my-orders`): chose **`/track`** as the single public entry point,
mirroring `/admin/login`'s role exactly but for the customer domain —
phone entry and OTP entry both live on this one URL (a client-side step
toggle, not two server routes), so there is exactly one entry point, not
several competing ones. An already-authenticated visitor hitting `/track`
is redirected straight to the protected shell instead of being asked to
re-verify.

The protected landing page is **`/track/(protected)/orders`** — deliberately
already named `orders` (not e.g. `/track/portal`) so Phase 3.4 Part 2 has
a natural, correctly-named home to fill in real order history, rather
than this phase inventing a placeholder name Part 2 would need to
rename. The `(protected)` route group's `layout.tsx` is this tree's
authorization gate, exactly mirroring `/admin/(protected)/layout.tsx`.

A "Track Orders" link was added to the site header (desktop) and mobile
nav sheet — without it, the feature would be built but genuinely
undiscoverable by a real visitor, which the brief's "customer visits →
Track Orders" flow implies should exist.

## Phone verification flow

```text
/track (phone step)
  → requestOtpAction({ phone })
    → requestOtp() normalizes, cooldown/rate-limit-checks, generates
      code, calls the OTP provider, persists a challenge (superseding
      any earlier one)
  → generic "sent" response, always — regardless of whether a Customer
    exists for this phone (see "Customer existence privacy")
/track (code step)
  → verifyOtpAction({ phone, code })
    → verifyOtp() validates the current challenge (exists, not expired,
      attempts not exhausted, code matches) and consumes it on success
  → createCustomerSession(phoneNormalized) — a fresh, unrelated-to-
    anything-client-supplied session token
  → redirect to /track/orders
```

## Customer existence privacy

**The core rule**: `requestOtp()` never checks whether a Customer exists
for the given phone — it operates purely on the phone number itself. A
real OTP is generated and sent (via the provider boundary) for *any*
syntactically valid phone, registered or not. This is deliberate, not an
oversight: it means the function's behavior, timing, and response are
**structurally identical** whether the phone belongs to a real Klasiq
customer or not — there is no code path that could accidentally leak
existence, because existence is never checked in the first place.

The Server Action (`requestOtpAction`) returns the same generic message —
*"If that number is registered with Klasiq, we've sent a verification
code."* — on every success, and the same cooldown/rate-limit/format
errors regardless of registration (these are phone-existence-independent
by construction, see "OTP resend abuse" below). Proven directly, not just
documented: `src/server/actions/customer-portal/__tests__/auth.test.ts`
asserts `requestOtpAction` returns a byte-identical response object for a
phone with a real Customer versus one without.

Only **after** successful OTP verification — i.e., the caller has already
proven they own that phone number — does the system check whether a
Customer exists, purely to decide what the portal shell shows them about
*their own* number. That is not an enumeration risk: someone who has just
proven ownership of a phone number learning whether *that same number*
has Klasiq orders reveals nothing to anyone else.

## OTP challenge architecture

`OtpChallenge` (additive migration, see "Database migration"):

```prisma
enum OtpPurpose {
  CUSTOMER_PORTAL_LOGIN
}

model OtpChallenge {
  id              String     @id @default(cuid())
  phoneNormalized String
  purpose         OtpPurpose
  codeHash        String
  expiresAt       DateTime
  attemptCount    Int        @default(0)
  consumedAt      DateTime?
  createdAt       DateTime   @default(now())
}
```

Not linked to `Customer` at all — a challenge can (and routinely does)
exist for a phone number with no Customer record. `purpose` exists as its
own enum (one value today) specifically so a future purpose — e.g. a
Phase 3.5 return/exchange re-verification — gets its own isolated
challenge stream rather than being mixed into portal-login's, without
needing a schema change when that day comes. Not over-generalized beyond
that: no generic "verification event" table, no unused fields for a
hypothetical need.

## OTP generation

`crypto.randomInt(0, 10**6)`, zero-padded to 6 digits
(`src/server/customer-portal/otp.ts`, `generateOtpCode`) — Node's CSPRNG-
backed, rejection-sampled, uniform primitive. **Never** `Math.random()`
(not cryptographically secure) and never a predictable sequence. 6 digits
is the standard length every real OTP delivery provider (WhatsApp
Business API, SMS gateways) expects, so Phase 3.6 can plug in a real
provider without any format change here.

## OTP storage / threat model

**Never stores the plaintext code.** Stored as a **scrypt** digest via
the newly-extracted `src/lib/scrypt-hash.ts` (`hashSecret`/
`verifySecretHash`) — the exact same primitive Phase 3's admin password
hashing already uses, now shared rather than duplicated. This was a
deliberate choice over a faster hash (SHA-256/bcrypt-lite): a 6-digit
code has only 1,000,000 possible values, so if this table ever leaked, a
**fast** hash would let an attacker brute-force every challenge's code in
well under a second. scrypt's memory-hard cost (the same parameters
already proven acceptable for interactive admin login) turns that into a
meaningfully expensive offline attack per challenge, without needing a
separate server-side pepper/secret — the codebase already has no such
secret-management convention, and reusing the proven per-record-salt
scrypt approach avoids introducing one. Comparison is via
`timingSafeEqual`, never a plain `===`.

## Expiration

**10 minutes** (`OTP_CONFIG.expiryMinutes`, env-overridable,
`src/lib/otp-config.ts`) — long enough that a customer reading a
WhatsApp/SMS message and typing it in isn't rushed, short enough that a
leaked/overheard code has a narrow window. Centralized in one config
object, never a scattered magic timestamp. Tested directly: a challenge
manually backdated past `expiresAt` fails verification with the correct
code (`EXPIRED`), and the identical flow with no backdating succeeds —
proving the boundary is enforced, not merely assumed.

## Attempt limit

**5 wrong guesses** (`OTP_CONFIG.maxAttempts`) per challenge. Checked
**before** comparing the code (so a locked challenge never even spends a
scrypt computation on a guess), incremented only on a wrong guess.
Concretely: guesses 1–5 are evaluated against the real code; the 6th (and
every subsequent) call is refused outright with `TOO_MANY_ATTEMPTS`,
**even if it's the correct code** — proven directly by a test that
performs exactly 5 wrong guesses, then verifies with the *actual* correct
code and confirms it's still refused. A locked challenge is not
automatically unlocked by anything except a brand-new OTP request
(respecting the resend cooldown), which supersedes it with a fresh
attempt count.

## OTP resend / abuse protection

Two independent, centralized bounds (`src/lib/otp-config.ts`):

- **Cooldown**: 45 seconds minimum between two requests for the same
  phone. Enforced **server-side** by comparing `now` against the latest
  challenge's `createdAt` — the client's own countdown UI is cosmetic
  only (resynced from the server's real `retryAfterSeconds` on an actual
  cooldown rejection), never trusted as the enforcement.
- **Rolling-window cap**: at most 5 requests per phone within a 60-minute
  window (a plain `COUNT(*) WHERE createdAt >= now - 60min`), bounding
  total messages even if someone waits out the cooldown repeatedly five
  times in a row. This is the primary defense against a single number
  driving unbounded provider sends — a real monetary cost once Phase 3.6
  wires up billed WhatsApp delivery, worth guarding against now even
  though today's dev provider is free.

Both are phone+purpose-scoped, not IP-scoped — see "Architecture debt"
for the honest limitation this implies.

## OTP replacement semantics

A new request **supersedes** every earlier still-active (`consumedAt:
null`) challenge for the same phone+purpose — implemented as a single
transaction that marks all prior actives consumed, then creates the new
one. At most one challenge is ever valid at a time. Proven directly: a
test requests twice (bypassing cooldown deterministically by backdating,
never by waiting), then confirms the **first** code no longer verifies
while the **second** does.

## OTP verification

`verifyOtp()` (`src/server/customer-portal/otp.ts`) does, in order:
normalize the phone; look up the current active challenge (query itself
filters `consumedAt: null`, so a replay of an already-used code is
invisible from the start, not merely rejected after being found);
check expiry; check the attempt limit; compare the code via
`verifySecretHash`; on a wrong guess, increment `attemptCount` and
return; on a correct guess, **atomically consume** the challenge via a
guarded `updateMany` (`WHERE id = ? AND consumedAt IS NULL`) — if a
concurrent call already consumed it (a genuine race, however unlikely),
the count is 0 and this call correctly reports failure rather than a
second "success" for the same challenge. Replay is proven to fail by a
dedicated test: verify once (succeeds), verify again with the identical
code (fails, `NO_ACTIVE_CHALLENGE`).

## Provider abstraction

`src/server/otp/provider.ts` — the *only* seam between OTP domain logic
and however a code is actually delivered:

```ts
export type OtpProvider = {
  sendOtp(params: { phoneNormalized: string; code: string; purpose: string }): Promise<void>;
};
```

`requestOtp()` calls only `provider.sendOtp(...)` and never knows or
cares whether that's WhatsApp, SMS, or today's development stand-in —
Phase 3.6 adds a real WhatsApp-backed implementation of this exact
interface with **zero change** to customer authentication itself. No
Meta/WhatsApp API is called anywhere in this phase; no `₹0.115/message`
or any other cost assumption appears in application logic (messaging
economics belong to a future phase's own concern, not this one's).

## Development/test provider

`ConsoleOtpProvider` (same file) — the *only* implementation that exists
today. Writes the code to the **server's own terminal** (never the
browser, never a URL/query parameter, never the database) with an
explicit `[DEV OTP — local development only, never shown to a real
customer]` prefix, so a developer manually exercising the portal locally
can complete the flow without Phase 3.6's not-yet-built real integration.

**This is not a hard-coded backdoor** — the code is still the real,
cryptographically random value from `generateOtpCode()`; only its
*delivery channel* differs. `getOtpProvider()` is the sole place that may
construct it, and it does so **only** outside `process.env.NODE_ENV ===
"production"`; in production it throws immediately (`getOtpProvider`)
rather than silently falling back to the console or fabricating success
— a genuine production deployment today would fail closed with a clean
"verification unavailable" customer-facing error until Phase 3.6 supplies
a real provider. `ConsoleOtpProvider` itself carries a second, redundant
production guard (defense in depth against a future refactor mistake).

For automated tests, `requestOtp()`/`verifyOtp()` accept an **injectable**
provider parameter — every test in `otp.test.ts` passes a fake, in-memory
provider that captures the sent code, so no test depends on (or triggers)
real console output, and none waits for or requires a real message of any
kind.

## Session architecture

`CustomerSession` — deliberately its **own** table, its **own** cookie
(`klasiq_customer_session`, distinct from `klasiq_admin_session`), and
its **own** module (`src/lib/customer-portal/session.ts`), never sharing
code or state with `AdminSession`/`getAdminSession()`. Same proven shape
as the admin session (opaque `randomBytes(32)` token, only its SHA-256
hash persisted, httpOnly/`sameSite: lax` cookie, `secure` in production,
reasonable expiry) — reused deliberately, not reinvented, but kept a
fully separate security domain per the brief's explicit instruction.

**Key design decision**: `CustomerSession` has **no relation to
`Customer`** — its only stored identity is `phoneNormalized`. Every
`getCustomerSession()` call resolves the `Customer` **fresh**, by that
phone, never from a cached `customerId` on the session row. This
directly implements "Customer resolution after OTP" below: a phone
verified before any `Customer` record exists still gets a working
session (which will start correctly reflecting a `Customer` the moment
one is created — e.g., by a later Counter sale — without needing to
re-verify), and there is no `customerId` anywhere in the session for a
caller to manipulate even in principle.

## Customer resolution after OTP

Phone ownership and Customer identity are two separate concerns.
`verifyOtp()` succeeding proves only phone ownership; it does **not**
create a `Customer`. If no `Customer` row exists for the verified phone,
the portal shell shows a plain, friendly "we couldn't find any orders for
this number yet" state — **never** a fabricated `Customer`, and never a
distinct internal error the visitor doesn't need to see. `getCustomerSession`'s
return shape makes this explicit: `{ phoneNormalized, customer: Customer |
null }` — callers must handle `null`, there's no way to accidentally treat
"no customer" as an error condition.

## Authorization helper

`getCustomerSession()` (`src/lib/customer-portal/session.ts`) is the
**one** primitive every current and future customer-portal route/action
uses — it takes **zero arguments**, its only input is the request's own
httpOnly cookie. `/track/(protected)/layout.tsx` calls it once and
redirects on `null`; the portal shell page calls it again (Server
Components can't share a request-scoped context across files the way
`getAdminSession()`'s own callers don't either) purely to read the
resolved session, not to re-authorize. Phase 3.4 Part 2 and Phase 3.5 are
expected to call this exact function rather than re-implementing cookie
parsing.

## Customer data boundary

There is no `customerId`, phone, order number, or any other
client-suppliable value anywhere in `getCustomerSession()`'s signature —
structurally, not just by convention, there is no parameter a caller
could change to redirect the lookup toward a different customer. The only
way to "become" a different customer is to possess that customer's actual
64-character random session token, which requires either stealing their
cookie or guessing a `crypto.randomBytes(32)` value — cryptographically
infeasible. Proven directly: a test creates two real Customers and two
sessions (one per phone), and confirms Customer A's session resolves only
Customer A, never Customer B, with no code path in between that accepts
an id.

## Existing secure order URL

`/order/[orderNumber]/[token]` (Phase 2) — **not touched in any way**.
`src/server/queries/orders.ts`'s `getOrderByNumberAndToken` still requires
both the order number and the secret access token; it does not depend on,
check, or interact with a customer-portal session in any way. The two are
independent access paths to related data, exactly as the brief requires:
the portal is an *additional* authenticated route to purchase history,
never a replacement for or dependency of the existing per-order link.

## Logout / session revocation

`customerLogoutAction` → `destroyCustomerSession()`: deletes the session
row named by the current request's own cookie and clears the cookie.
Proven directly: a session that resolves successfully before logout
resolves to `null` immediately after, and the underlying database row is
gone (not just the cookie) — a stolen/cached cookie value cannot be
replayed after logout.

## Session fixation

`createCustomerSession` **always** mints a brand-new `randomBytes(32)`
token — there is no code path anywhere that accepts or promotes a
client-supplied token into authenticated state. It is called exactly
once, from exactly one place (`verifyOtpAction`, immediately after
`verifyOtp()` returns success), so a successful OTP verification always
produces a fresh session rather than reusing or upgrading any prior
cookie value.

## Multiple devices

Deliberately **allowed**, not restricted — nothing in `createCustomerSession`
invalidates any other session for the same phone. This matches the
brief's explicit "do not over-engineer" instruction and the codebase's
existing precedent (admin sessions aren't single-device-limited either).
Logout only ever removes the **one** session named by its own request's
cookie, never every session for that phone/customer.

## Mobile UX

`TrackOrdersForm` (`src/components/customer-portal/track-orders-form.tsx`):
48px-tall (`h-12`) inputs and buttons throughout; `inputMode="tel"` for
the phone step and `inputMode="numeric"` for the 6-digit code step
(correct mobile keyboard on both); a single numeric `<Input>` for the
code (not six separate boxes — deliberately, see "Accessibility" below);
masked-phone confirmation text ("Sent to ••••••3210") using only what the
visitor themselves typed; a visible, resyncable resend countdown;
secondary actions ("Change number", "Resend code") sized to a minimum
44px touch target even though their text is small. Single-column,
`max-w-sm` layout — no horizontal scroll at any width down to 320px.

## Accessibility

- Every input has an associated `<Label>`.
- Errors use `role="alert"`; the resend-notice/status text uses
  `role="status"` (implicit `aria-live="polite"`) so a screen-reader user
  hears state changes without needing to re-focus anything.
- Both inputs' `aria-invalid`/`aria-describedby` point at the specific
  error message when one is showing, so assistive tech associates the
  error with the right field.
- **Deliberately one plain numeric input for the 6-digit code, not six
  separate single-character boxes** — the latter is a common but
  genuinely harder-to-use-with-a-screen-reader/harder-to-paste pattern; a
  single field with `inputMode="numeric"` and `autoComplete="one-time-code"`
  (which also lets a browser/OS offer to autofill an SMS-delivered code
  once a real provider exists) is the simpler, more accessible choice,
  exactly matching the brief's explicit "do not create six visually
  attractive OTP boxes that are inaccessible" guidance.
- No color-only feedback — every error state pairs an icon with text.
- Focus states are the design system's existing `focus-visible` styling
  (`Input`/`Button`), unchanged.

## Security review

- **OTP randomness**: `crypto.randomInt`, CSPRNG-backed, uniform,
  rejection-sampled — never `Math.random()`. Verified directly (test
  asserts the shape; code review confirms the primitive).
- **OTP storage**: scrypt digest, per-challenge random salt, never
  plaintext — see "OTP storage / threat model" above for the full
  reasoning on why a fast hash would be inadequate for a 6-digit space.
- **OTP brute-force resistance**: bounded two ways — the attempt limit
  (5 guesses per challenge, enforced server-side before any comparison)
  and scrypt's cost (meaningful even if the table leaked entirely).
- **OTP replay**: proven to fail — a consumed challenge is invisible to
  the very query that looks it up (`consumedAt: null` in the `WHERE`
  clause itself), not merely rejected after being found.
- **OTP expiration**: enforced on every verification attempt, proven with
  a deterministically-backdated challenge (never a real wait).
- **OTP resend abuse**: cooldown (45s) + rolling-window cap (5/hour),
  both phone-scoped, both enforced server-side regardless of what any
  client-side timer shows.
- **Customer enumeration**: `requestOtp()` structurally cannot leak
  existence (it never checks); proven with a byte-identical-response
  test, not just documented.
- **Session token generation**: `randomBytes(32)`, base64url-encoded —
  same proven primitive as `AdminSession`.
- **Session token storage**: only the SHA-256 hash is persisted; the
  test suite directly confirms the raw cookie value is never itself a
  valid database lookup key and never appears as a substring of the
  stored hash.
- **Cookie security**: `httpOnly` (never readable from client JS, and
  never stored in localStorage anywhere in this codebase), `sameSite:
  "lax"`, `secure` gated on production, scoped to `/` (the portal itself
  spans multiple future paths, unlike admin's `/admin`-scoped cookie).
- **Session fixation**: a fresh token is minted on every successful
  verification; nothing promotes a pre-existing or client-supplied value.
- **Cross-customer authorization**: structurally impossible through any
  user-controlled id — `getCustomerSession()` takes no arguments at all;
  proven directly with a two-customer test.
- **Admin/customer auth separation**: entirely separate tables, cookies,
  and modules; zero shared code paths between `getAdminSession()` and
  `getCustomerSession()` beyond the (now-shared, behavior-identical)
  generic `hashSecret`/`verifySecretHash` scrypt utility.
- **CSRF considerations for logout/session-changing actions**: `logout`
  and `verifyOtpAction` are both Next.js Server Actions, which Next.js
  itself protects with same-origin checks on the request (the framework's
  built-in Server Action CSRF mitigation, unchanged from every other
  Server Action already in this codebase, e.g. `adminLogout`) — no
  additional custom CSRF token was introduced, consistent with how the

  guarantee.

  the full diff for stray `console.log`/OTP-adjacent logging and found
  none elsewhere. `placeOrderForBasket`-style "never log the secret"
  discipline (established in earlier phases) was followed for the OTP

## Performance review

- `getCustomerSession()`: at most 3 queries per authenticated request
  (session lookup by unique `tokenHash`, a best-effort non-blocking
  `lastUsedAt` update, and a `Customer` lookup by unique
  `primaryPhoneNormalized`) — both lookups hit unique-indexed columns,
  no table scans. This is the same cost shape as `getAdminSession()`'s
  own session+join lookup.
- `requestOtp()`: one `findFirst` (indexed), one `count` (indexed, same
  compound index), one provider call, one transaction (`updateMany` +
  `create`, both on the same indexed columns) — no N+1 pattern, no
  unindexed scan.
- No Redis or other new infrastructure was introduced — every check
  (cooldown, rate limit, session lookup) is a single indexed Postgres
  query, appropriate at this application's current scale. See
  "Architecture debt" for the honest limitation this implies for
  distributed/IP-based rate limiting specifically.

## Architecture debt

Evaluated honestly, per the brief's explicit request — **do not pretend
these exist**:

- **Production WhatsApp OTP provider**: does not exist. The provider
  boundary (`OtpProvider`) is designed specifically so Phase 3.6 can add

  but until that phase, production OTP sending is refused outright
  (fail-closed), not degraded to a fake success.
- **Distributed/IP rate limiting**: genuinely absent. Today's cooldown
  and rolling-window cap are phone-number-scoped only — a single actor
  rotating through many different phone numbers from one IP/device isn't
  bounded by anything in this phase. No infrastructure for this
  (Redis, a WAF-level limiter, etc.) exists in this project, and adding
  one solely for this phase would be exactly the kind of speculative
  infrastructure the brief asked not to introduce without demonstrated
  need. Honestly flagged, not hidden.
- **OTP delivery monitoring**: no metrics/alerting on send failures,
  delivery latency, or provider error rates — reasonable once a real
  provider exists (Phase 3.6), not meaningful for a console dev stand-in.
- **Multi-device session management UI**: sessions across devices are
  allowed (see "Multiple devices") but there is no "see your active

- **Session revocation UI**: beyond self-logout, there's no admin-side

- **Provider-specific retry strategy**: `ConsoleOtpProvider` has none
  (writing to the console can't meaningfully fail in a way worth

  timeout/retry policy, which is Phase 3.6's concern, not designed here

  reasonable foundation for a future provider to build retries on top of,

### Portal query architecture

Two new functions, `src/server/queries/customer-portal/orders.ts`:

```ts
getOrdersForAuthenticatedCustomer(customerId: string)
getOrderForAuthenticatedCustomer(orderNumber: string, customerId: string)
```

Both take `customerId` as their **only** identity input, and both bake
ownership directly into the Prisma `WHERE` clause — never fetch-then-check.
`getOrderForAuthenticatedCustomer` in particular: `db.order.findFirst({
where: { orderNumber, customerId } })` — a request for an order number
that exists but belongs to someone else returns `null`, **structurally
identical** to "this order number doesn't exist at all." There is no code
path that could distinguish the two cases, so neither can a caller
(legitimate or malicious) probing the route.

### Authorization boundary

`customerId` is supplied to both functions **only** from
`(await getCustomerSession()).customer.id` — resolved server-side from
the verified session cookie, never from a URL parameter, request body,
hidden field, or any other client-controlled value. Both portal pages
(`/track/orders`, `/track/orders/[orderNumber]`) call `getCustomerSession()`
themselves (in addition to the protected layout's own gate) purely to
read the resolved `customer` — this is not a second authorization check
layered on top of the layout's redirect, it's simply how a Server
Component gets the already-verified data it needs.

The order-detail page additionally short-circuits to `notFound()` (not a
special error) whenever `session.customer` is `null` — a verified phone
with no linked Customer cannot own any order number at all, so there's no
lookup to even attempt.

### My Orders UI

`/track/(protected)/orders/page.tsx` + `OrderHistoryCard`
(`src/components/customer-portal/order-history-card.tsx`): newest-first
list, each card showing order number, date, status, source
("Online Order" / "Purchased in Store"), item count + total, fulfillment
type, and a large "View Order" link. An empty state ("No Klasiq orders
yet." + a "Start shopping" link) renders when `session.customer` is
`null` or has zero orders — never an error, never a hint that anything
went wrong.

### Online + Counter convergence, guest exclusion, historical exclusion

All four are the direct, structural consequence of one query condition
(`where: { customerId }`), proven with real Postgres integration tests
rather than just asserted:

- An **ONLINE** order with `customerId` set appears.
- A **customer-linked COUNTER** order (the cashier selected/created this
  same Customer — Phase 3.2/3.3's "Counter/online identity convergence")
  appears in the exact same list — a customer's Klasiq history is their
  relationship with Klasiq across channels, not just their website
  history.
- A **guest Counter sale** (`customerId: null`) never appears for anyone
  — not by a special exclusion filter, but because `null` can never equal
  a real customer's `id` in the `WHERE` clause. No fuzzy matching by name/
  phone-text/date/amount/school was implemented or considered — an order
  either has this exact `customerId` or it doesn't.
- A **historical, unlinked order** (`customerId: null`, predating Phase
  3.1/3.3) never appears either, for the identical reason — even for a
  customer who now exists and even if the old order's `customerName`/
  `customerMobile` snapshot happens to match them. No automatic backfill
  was performed or attempted. A future admin-assisted "attach historical
  guest purchase" tool could exist, but is explicitly out of scope here.

Both directions of cross-channel convergence (ONLINE-then-COUNTER and
COUNTER-then-ONLINE for the same Customer) are proven by dedicated tests,
not just asserted to be symmetric by construction.

### Order detail route

`/track/(protected)/orders/[orderNumber]/page.tsx` — the order number is
a normal, visible URL segment (needed for navigation/sharing within the
portal), but it authorizes nothing by itself; only the session does. This
is deliberately **independent** of the existing

B's real order number requested directly →
`getOrderForAuthenticatedCustomer` returns `null` → the page calls

### Tracking data model audit

**No status-event/transition history is persisted anywhere in this
schema** — `Order` has only a current `status` column and `updatedAt`;
there is no separate audit table for *when* each transition happened
(unlike `InventoryAdjustment`, which tracks stock changes specifically,
not order-status changes). Confirmed by reading the full `Order` model
and grepping for any status-history table — none exists.

**Consequence, honestly enforced in code**: the tracking timeline
(`src/lib/order-tracking.ts`, `getOrderTracking`) shows only **completed
/ current / future** stage markers derived from the current authoritative
status — it never fabricates a timestamp like "Packed at 2:14 PM" for
data that was never recorded. This is a pure function of two existing
database columns (`fulfillmentType`, `status`); nothing invented.

### Fulfillment-specific tracking

Two real stage sequences, both built only from `OrderStatus` values that
are genuinely reachable for that fulfillment type (per
`FULFILLMENT_ONLY_STATUS` in `order-lifecycle.ts`, not a separately
invented rule):

- **Store Pickup**: Order Placed → Confirmed → Preparing → Ready for
  Pickup → **Collected** (the one label override this module makes —
  "Collected" reads more honestly than the generic "Delivered" for an
  order the customer walked in and picked up themselves; every other
  label is `ORDER_STATUS_LABEL` verbatim).
- **Local Delivery**: Order Placed → Confirmed → Preparing → Out for
  Delivery → Delivered.
- **Counter Handover**: no multi-stage timeline at all — a single
  "Purchased in Store / Completed" state, because (see "Existing
  infrastructure audited" above) a real Counter order's status is always
  exactly `DELIVERED` and always was from the moment of sale. Building a
  fake delivery journey for an already-completed in-person handover would
  be dishonest, not merely unnecessary.
- **Cancelled**: takes priority over all of the above, for **every**
  fulfillment type — a clear terminal "Cancelled" state, never future
  stages rendered as if they might still happen. No refund-processing
  claim is made or implied.

### OTP cleanup — genuine gap found and fixed

**The gap**: `requestOtp()` already marked superseded/consumed challenges
`consumedAt` (Part 1), but nothing ever **deleted** old rows — the
`otp_challenges` table would have grown by one row per request, forever,
with no bound.

**The fix**: `cleanupExpiredOtpChallenges()`
(`src/server/customer-portal/otp.ts`) deletes any challenge older than a
24-hour retention window (real codes only ever live 10 minutes by
default — 24 hours is a generous grace period for debugging a recent
issue, not a "just in case" hoard). Runs **opportunistically**, once per
successful `requestOtp` call, as a best-effort fire-and-forget operation
(`.catch(() => {})`) that can never block or fail a real OTP request — no
background worker, no cron, no new infrastructure, per the brief's
explicit instruction. At this shop's real request volume (a handful of
OTP requests a day), a plain `deleteMany` with no dedicated index is not
a performance concern; a genuinely high-volume deployment might
eventually want a scheduled job instead (see "Architecture debt").
Tested directly: a backdated-past-retention challenge is deleted, a
recent one is not, and calling it with nothing to clean up is safe.

### Session cleanup — genuine gap found and fixed

**The gap**: `getCustomerSession()` already opportunistically deleted the
**one** expired session it happened to read (Part 1) — but a session
that expires and is **never read again** (a customer who verified once
and never came back) would never be cleaned up by that path alone,
accumulating indefinitely.

**The fix**: `cleanupExpiredCustomerSessions()`
(`src/lib/customer-portal/session.ts`) deletes every session whose
`expiresAt` has already passed (no grace period needed — an expired
session is unconditionally useless the instant it expires, unlike an OTP
challenge). Runs opportunistically once per new login
(`createCustomerSession`, a natural, moderate-frequency write point),
best-effort, never blocking a real login. Tested directly: an
expired-but-never-read session is deleted, a valid one is untouched, and
calling it with nothing to clean up is safe.
